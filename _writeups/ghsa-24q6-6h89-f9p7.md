## Summary

The AutoGPT platform verifies every bearer token against `JWT_VERIFY_KEY`, and that key ships hardcoded in the default env files committed to the public repository. The signing secret is `your-super-secret-jwt-token-with-at-least-32-characters-long`, published in both `.env.default` and `backend/.env.default`. Anyone who knows it, which is anyone with a browser and the repo URL, can mint a token that the backend accepts as a fully authenticated user, including an admin. For a deployment left on the default, this is an unauthenticated takeover of the entire API.

## Where it lives

Token verification happens in `autogpt_libs/auth/jwt_utils.py`. The decode uses the configured secret directly and only checks the signature, algorithm and audience:

<!-- bug: settings.JWT_VERIFY_KEY, :: the token is checked against the key the repository ships -->
```python
def parse_jwt_token(token: str) -> dict[str, Any]:
    settings = get_settings()
    try:
        payload = jwt.decode(
            token,
            settings.JWT_VERIFY_KEY,
            algorithms=[settings.JWT_ALGORITHM],
            audience="authenticated",
        )
        return payload
```

`settings.JWT_VERIFY_KEY` resolves to the shipped default. In `backend/.env.default` line 33:

<!-- bug: JWT_VERIFY_KEY=your-super-secret-jwt-token :: the signing secret is published in the default env file -->
```
JWT_VERIFY_KEY=your-super-secret-jwt-token-with-at-least-32-characters-long
```

and the matching Supabase-side `JWT_SECRET` in the platform `.env.default` line 7 carries the same string. Nothing refuses to start on the default value.

Once a token is decoded, `verify_user` in the same file trusts its claims wholesale. The caller's identity is just the `sub` claim, and admin is just a string field:

<!-- bug: user_id = jwt_payload.get("sub") :: identity is the sub claim the attacker writes -->
<!-- bug: jwt_payload["role"] != "admin" :: admin is a field in the token the attacker writes -->
```python
    user_id = jwt_payload.get("sub")

    if not user_id:
        raise HTTPException(status_code=401, detail="User ID not found in token")

    if admin_only and jwt_payload["role"] != "admin":
        raise HTTPException(status_code=403, detail="Admin access required")
```

So a forged payload that sets `sub` to any victim's id and `role` to `admin` passes both gates.

## Impact

I wrote a standalone PoC that forges a token with PyJWT, signs it HS256 with the public secret, and runs it back through the same `jwt.decode` call the backend uses. It is accepted. Setting `role` to `admin` clears the `admin_only` check as well.

The chain needs no credentials and no prior access. Pick any `sub` and the backend treats the request as that user, reading and mutating their agents, integrations and runs. Set `role` to `admin` and the forged token reaches admin-only endpoints. Combined with the equally public default `ENCRYPTION_KEY`, an attacker can also pull and decrypt the stored OAuth tokens and provider API keys those accounts hold. This is a complete authentication bypass against any instance running the shipped configuration.

## Fix

Treat the shipped secret as a fatal misconfiguration rather than a convenience. Refuse to start when `JWT_VERIFY_KEY` is empty or equal to a known published default, so a deployment cannot silently run on the committed value. The default env files should carry a placeholder that fails this check, with setup docs that force the operator to generate a fresh secret before first boot.
